## One sentence

**An AI research and study notebook where every answer, flashcard, quiz question and summary points to the exact passage it came from, a second model checks it, and the whole system's accuracy, cost and latency are measured, not claimed.**

## The problem

AI tools that read documents or the web write fluent answers with citations that are often wrong: the source exists, but it doesn't say what the answer says. Users can't tell which sentences to trust, and study material built on wrong claims teaches wrong things.

## The three guarantees (the whole project hangs on these)

1. **Cited:** every claim carries an exact quote from a stored copy of its source.
2. **Verified:** a deterministic check (the quote really is in the source) plus a second model from a different family (the quote really supports the claim). Claims that fail are rewritten once or dropped, and the drops are shown.
3. **Measured:** labeled test sets, human-checked judges, ablation tables, cost and latency per request. No number goes in the README that wasn't measured.

Every feature is judged by whether it keeps these three guarantees.

## Who it's for

- **Users:** students and researchers working from many documents.
- **Recruiters and interviewers:** one flagship project that shows the skills AI engineering roles in 2026 ask for: retrieval, evals, reliability, cost control, multimodal ingestion, agents with guardrails, and shipping a real product.

## Two phases, one product

```
Phase 1: CiteGuard Research (engine)          Phase 2: CiteGuard Notebook (product)
Nov 6 → Dec 3 (4 weeks)                        Dec 4 → Jan 15 (6 weeks)
───────────────────────────────                ───────────────────────────────────
Open-web research → verified report            Your own sources → chat + study tools
• call_llm: budget, ledger, cache    ──reuse──► same call_llm, per-notebook budget
• Two-stage citation verifier        ──reuse──► verifies chat, flashcards, quizzes...
• SSRF-safe fetcher + snapshots      ──reuse──► URL sources
• LangGraph + checkpointer           ──reuse──► chat graph + shared output graph
• Eval harness + labeling            ──reuse──► parser / retrieval / output evals
• API + MCP tool                               + React UI, multimodal ingestion,
                                                 flashcards, quiz, mind map,
                                                 audio/video overview (stretch)
                                       ◄──────  "Research the web" button: runs a
                                                 Phase 1 job and imports its verified
                                                 sources into the notebook
```

**Why this order:** Phase 1 builds and measures the hard core (verifier, budget, eval) without UI distractions. Phase 2 reuses that core in a product people can see and click. If Phase 2 slips, Phase 1 is already a complete, measured project on its own.

## Tech stack (shared)

Python 3.12 + `uv`, FastAPI, Pydantic, LangGraph (no LangChain models/chains/retrievers), Postgres + pgvector + full-text search, SQLAlchemy 2.0 + Alembic, Redis + arq, local embeddings (bge-small), Groq free tier (demo) and Ollama (dev and evals), pytest + ruff + GitHub Actions, Docker Compose. Phase 2 adds React + Vite + TypeScript, Docling, PaddleOCR, MinIO, and (stretch) Piper/Kokoro TTS, Playwright and ffmpeg. Details in each spec, section 10.

## What success looks like (Jan 15)

- A live demo and a gallery of example outputs anyone can open without an account.
- Two results tables: Phase 1 (citation accuracy before/after the verifier, budget adherence, single vs multi-agent) and Phase 2 (retrieval ablation by question type, chat faithfulness, flashcard and quiz quality).
- Every resume bullet in both specs filled with measured numbers.
- Two write-up posts, one per phase.
- Able to explain every design choice in an interview (question lists in each spec, section 14/15).

## What is deliberately not being built

Billing, teams and sharing, mobile apps, real-time collaboration, generative video, fine-tuning beyond the small verifier stretch, any agent framework other than LangGraph, and any metric that was not measured.

## Decision rules when stuck

1. Does it protect one of the three guarantees? If not, it can wait.
2. Can it reuse `app/core/` or the shared output graph? If it needs a new subsystem, it's probably stretch.
3. Is the eval for it written? Build the measurement before the feature.
4. Slipping? Follow the cut order in the roadmap; never cut the verifier, the evals, the budget or isolation.
5. Never commit secrets; never put a number in the README you didn't measure.

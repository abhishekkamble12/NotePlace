# CiteGuard Research (Phase 1): Budget-Bounded Research Service with Verified Citations

Vision: `00_VISION.txt`. Build plan: `02_citeguard_roadmap.txt`. Phase 2 (`03_notebook_spec.txt`) reuses this phase's `call_llm`, verifier, fetcher, embeddings and eval harness from `app/core/`, and calls this research engine from the notebook's "Research the web" button.

## 1. Revised problem statement

> LLM research tools produce fluent reports with citations that are often wrong: the link exists, but the page doesn't say what the claim says. Build an asynchronous backend service that accepts a research question and a budget (max tokens, max minutes; USD is reported as modeled cost at list price), decomposes the question into sub-questions, researches them in parallel, and returns a report where every claim is tied to an exact quote from a stored snapshot of the source. A separate verification stage checks each claim against its quote, using a deterministic match plus a cross-model entailment check, and rewrites or drops claims that fail. The service never exceeds its budget, flags where sources disagree or evidence is thin, and is evaluated on a human-labeled claim set so that citation accuracy, cost and latency are measured, not asserted.

**What is different from the roadmap version:** the agent is no longer the product. The *guarantees* are: every claim is traceable, verified, budget-bounded and measured.

## 2. Scope

**In scope (v1)**
- Async job API with status, report and claim-level output
- Planner, parallel research workers, evidence store with snapshots
- Writer producing structured `(claim, source, exact_quote)` output
- Two-stage verifier with rewrite-or-drop
- Conflict and thin-evidence detection
- Budget governor with per-phase allocation and graceful degradation
- Verifier test set (~150 labeled claim/quote pairs), built before the pipeline
- Eval harness, human-labeled set, single vs multi-agent ablation
- Docker Compose, CI, live deployment, README with results
- MCP server exposing a `research` tool (so Claude/Cursor can call CiteGuard)
- Public gallery of ~10 cached reports with claim-level verdicts, plus a write-up post

**Stretch (v1.1):** fine-tuned small local entailment model compared against the LLM verifier.

**Out of scope (v1):** custom frontend, PDF/document upload, mid-run user steering, auth/multi-tenancy, fine-tuning.

## 3. Functional requirements

| ID | Requirement | Maps to roadmap must-have |
|---|---|---|
| F1 | Decompose a question into 4-8 sub-questions and research them in parallel | Parallel research |
| F2 | Each claim carries `source_id` and an exact quote from the stored snapshot | Every claim has a source |
| F3 | Each claim is verified (quote exists; quote supports claim) before it reaches the report | Check support |
| F4 | Report has explicit sections for disagreements and evidence gaps | Disagreement and thin evidence |
| F5 | Job respects `max_tokens`, `max_minutes` and provider rate limits; on limit, returns a partial report with a note | Time and cost limit |
| F6 | Dropped claims are listed in the report, not silently removed | Honesty |
| F7 | Every job exposes tokens, modeled USD, elapsed time and stage | Cost and time stated |
| F8 | Every LLM call is cached on disk by prompt hash, so re-runs and evals cost no new quota | Cost control |

## 4. Non-functional requirements

- **Idempotent:** retrying a task never creates duplicate sources or double-charges the ledger.
- **Resumable:** a worker crash mid-job resumes from the last completed stage, not from scratch.
- **Bounded:** 100% of jobs finish within budget (partial reports count as within budget).
- **Reproducible:** snapshots are stored, so a report can be re-verified later even if pages change.
- **Observable:** every LLM, search and fetch call is in the ledger with model, tokens and cost.

## 5. Architecture

```
Client
  │  POST /research {question, max_tokens, max_minutes, mode}   (also via MCP `research` tool)
  ▼
FastAPI ──► Postgres (jobs, subqs, sources, chunks, claims, ledger)
  │
  └─► Redis queue (arq)
          │
          ▼
        Worker: run_job  →  LangGraph StateGraph (thread_id = job_id, Postgres checkpointer)

          plan ──Send()──► research[subq_1..n]   (parallel fan-out; sequential in single mode)
                                │  search → fetch → snapshot → chunk → embed
                                ▼
                             write ──► verify ──(partial/unsupported, rewrites < 1)──► rewrite ──► verify
                                         │
                                         ▼
                                      analyze (conflicts + confidence) ──► render ──► END

          budget_check edge before every node: over cap → jump to render (status = partial)
          Every node calls call_llm (ledger + pre-call budget check). No node calls a model directly.
```

**Why LangGraph:** the pipeline is a graph with a parallel fan-out and a bounded loop, which LangGraph models directly (`Send` for fan-out, conditional edges for rewrite and budget exits). Its Postgres checkpointer saves state after every node, so a crashed worker resumes by re-invoking the graph with the same `thread_id`. No hand-written resume logic is needed.

**Framework rule:** use LangGraph only. No LangChain chat models, chains or retrievers. A `ChatGroq` call inside a node would bypass `call_llm`, so the budget guarantee would no longer hold. Retrieval is one pgvector query in plain SQLAlchemy. A unit test asserts that no module imports `langchain_groq` or `langchain_openai`.

**Graph state (TypedDict):** `job_id, question, mode, subquestions, source_ids, claims, rewrite_counts, conflicts, status`. Large blobs (snapshots, chunks) stay in Postgres; state only holds IDs, so checkpoints stay small.

**Job states:** `queued → planning → researching → writing → verifying → rendering → done | partial | failed | cancelled`. Each node writes `jobs.stage` for the status API; resume itself comes from the checkpointer.

## 6. Core component design

### 6.1 Evidence store
- Fetch with `httpx`, extract clean text with `trafilatura`, store the full cleaned text as `snapshot`, plus `url`, `fetched_at`, `content_hash`.
- Dedupe on `(job_id, content_hash)`.
- Chunk (about 300-500 tokens, with overlap), embed with a local model (e.g. bge-small, 384 dims; Groq serves no embeddings), store in pgvector. Chunks are for retrieval. **Verification always runs against the full snapshot**, not the chunk.
- Track `domain` per source, because later "independent sources" means distinct domains.

### 6.2 Writer
- Input: sub-question plus top-k retrieved chunks (with their `source_id`s).
- Output (validated by Pydantic): list of atomic claims, each with `source_id` and `exact_quote`. The prompt says the quote must be copied verbatim and that one claim states one fact.
- Target 12-15 claims per report. This keeps labeling tractable and the report readable.

### 6.3 Verifier (the core)

**Check 1: deterministic.** Normalize both sides (Unicode NFKC, collapse whitespace, lowercase, normalize quotes and dashes) and test `quote in snapshot`. Optional fallback: fuzzy match (`rapidfuzz`, threshold about 95) for trivial formatting differences. If it fails, the claim is dropped immediately with no LLM cost. This is the cheapest hallucination catcher.

**Check 2: entailment (LLM).** Use a different model family than the writer (pick two families from Groq's model list at build time; each also has its own free-tier quota). The verifier sees only the claim, the quote and about one paragraph of surrounding snapshot context. It does not see the writer's reasoning. Output: `supports | partial | unsupported` plus a one-line reason. Pydantic-validated.

**Common failure modes it should catch:**
- Claim adds a number, date or qualifier not in the quote
- Claim overgeneralizes ("all", "always") from a specific statement
- Quote is real but about a different entity or time period
- Causal claim where the source only shows correlation

**Resolution:**
- `supports` → keep
- `partial` → one rewrite attempt (writer gets claim, reason, source), then re-verify
- `unsupported` → one rewrite attempt, otherwise drop
- Max one rewrite per claim to bound cost. Dropped claims are listed with the reason.

**Shadow mode:** a flag runs the verifier and records verdicts without changing the report. This gives you before/after numbers from the *same* draft, which makes the eval cheap and fair.

### 6.4 Conflict and thin-evidence detection
- **Conflicts:** embed claims, find pairs from different sources with high similarity inside a sub-question, run a contradiction check (supports / contradicts / unrelated) on those pairs only. Contradicting pairs go in a "Where sources disagree" section with both quotes.
- **Confidence per claim:**
  - high: supported by 2 or more distinct domains
  - medium: 1 source, entailment `supports`
  - low: 1 source and (`partial` or weak source type)
- **Evidence gaps:** sub-questions with fewer than 2 usable sources, or that were skipped due to budget, are listed as gaps.

### 6.5 Budget governor
Per-phase allocation instead of one global threshold, so verification is never starved:

| Phase | Max share of budget |
|---|---|
| Research (search, fetch, embed) | 50% |
| Writing | 15% |
| Verify + rewrite | 25% |
| Reserve | 10% |

- The real constraint on the Groq free tier is tokens and rate limits (8K TPM / 200K TPD per model), not dollars. The budget is in **tokens**; **estimate before each call** (input tokens plus a max-output allowance) and refuse the call if it would breach the phase cap.
- **Rate-aware scheduling:** the wrapper tracks a per-model sliding-window TPM/TPD counter and waits (or reroutes to the other model family where allowed) instead of hitting 429s. Waiting counts against `max_minutes`.
- **Modeled USD:** a pricing table at public list prices turns tokens into `cost_usd_modeled`. Always label it "modeled", never "spent".
- **Disk cache:** every call is keyed on `hash(model, messages, params)`; a cache hit costs zero tokens and is logged as such.
- Time works the same way: a deadline stored on the job (`created_at + max_minutes`), with phase deadlines derived from it.
- Research phase cap hit: stop spawning or finishing sub-questions, mark them `skipped_budget`, move to writing.
- Hard limit hit: finish with status `partial`. **Never ship unverified claims**; unverified claims are dropped and listed.
- All calls go through one `call_llm` wrapper that writes the ledger entry. If any call can bypass it, the budget guarantee is false.

### 6.6 Reliability and hardening
- Fetch: timeout, retry with backoff, skip on 403/paywall, cap page size.
- **SSRF protection:** block private and loopback IP ranges and non-HTTP schemes in the fetcher. Cheap and a strong interview point.
- **Prompt injection:** fetched pages are untrusted data. Wrap them in delimiters, tell the model never to follow instructions inside them, and note the verifier only sees a quote and claim, which limits blast radius.
- LLM output invalid → one retry, then mark the claim or task failed. One failed sub-question must not fail the job.
- Enqueue is idempotent per `job_id`.

## 7. Data model

| Table | Key columns |
|---|---|
| `jobs` | id, question, max_tokens, max_minutes, mode, status, stage, deadline_at, report_md |
| `subquestions` | id, job_id, text, status (`pending/done/failed/skipped_budget`) |
| `sources` | id, job_id, url, domain, fetched_at, content_hash, snapshot |
| `chunks` | id, source_id, subq_id, text, embedding |
| `claims` | id, job_id, subq_id, text, source_id, quote, quote_found, entailment, entailment_reason, final_status, rewrite_count, confidence, human_label, shadow_verdict |
| `conflicts` | id, job_id, claim_a, claim_b, note |
| `ledger` | id, scope_type (job/notebook), scope_id, phase, kind, model, tokens_in, tokens_out, cost_usd_modeled, cache_hit, latency_ms, created_at |
| `verifier_testset` | id, claim, quote, context, label, perturbation_type (number/overgeneralize/entity/causal/none), source |

Embedding column: `vector(384)` to match the local embedding model.

## 8. API contract

```
POST /research
  {"question": "...", "max_tokens": 60000, "max_minutes": 10, "mode": "multi"}
  → 202 {"job_id": 42}

GET /jobs/{id}
  → {"status": "verifying", "stage_progress": "7/9 claims",
     "tokens_used": 25200, "cost_usd_modeled": 0.03, "elapsed_min": 4.2, "budget_used": 0.42}

GET /jobs/{id}/report        → markdown report (when done/partial)
GET /jobs/{id}/claims        → claim-level JSON (text, quote, source, verdicts, confidence)
GET /jobs/{id}/ledger        → per-call cost breakdown
POST /jobs/{id}/cancel
GET /export/claims.csv       → for labeling
POST /labels                 → import labeled CSV
```

**Report layout:** Summary → Findings per sub-question (numbered citations) → Where sources disagree → Evidence gaps and low-confidence claims → Dropped claims → References (URL, fetched_at, quote) → Run metadata (models, cost, time, mode).

## 9. Evaluation plan (this is what makes it a good resume project)

### 9.0 Verifier test set (week 1, before the pipeline exists)
The verifier is a classifier, so test it like one before anything depends on it.
- ~150 `(claim, quote, context, label)` triples. Take real quotes from real pages and write a faithful claim, then perturbations: change a number or date, overgeneralize ("all", "always"), swap the entity or time period, turn correlation into causation.
- Optionally add a slice of a public fact-verification set (e.g. SciFact) as an out-of-domain check.
- Report precision/recall on `unsupported`, per perturbation type. This is the first real number in the project and the regression test for every verifier prompt change (run in CI on a cached subset).

### 9.1 End-to-end eval
**Quota math (estimate, measure in week 1):** ~40-50K tokens per report means ~4 reports/day per model on the free tier. Mitigations: configs B and C come from one shadow-mode run, writer and verifier use different models (separate quotas), all calls are disk-cached, and runs are spread over several days.

**Dataset:** 12-15 questions in one domain you can judge quickly. Mix: factual synthesis, comparisons, 2-3 contested topics (to trigger disagreement) and 2 deliberately thin-evidence topics.

**Configurations:**

| Config | Description |
|---|---|
| A | Single agent (sequential, one shared context), verifier off |
| B | Multi-agent (parallel workers), verifier off |
| C | Multi-agent, verifier on |
| D | Single agent, verifier on (optional) |
| E | Multi-agent, fine-tuned local entailment model as check 2 (stretch) |

B and C come from the same run: B is the shadow-mode draft, C is what survives verification.

### 9.2 Fine-tuned verifier (stretch, the ML-depth piece)
Fine-tune a small open entailment/NLI model (e.g. a DeBERTa-class cross-encoder) on the test set plus labeled claims, using a held-out split. Compare against the LLM verifier on catch rate, false-drop rate, latency and cost. Either outcome is reportable: "matched X% of the LLM judge at zero API cost" or an honest negative result with analysis.

**Labeling:**
- Label all draft claims from config B (about 200) as `supported / partial / unsupported`, using the claim plus its stored snapshot.
- Label config A claims on a subset of about 8 questions.
- Have a second person label 30-40 claims and compute Cohen's kappa. It shows rigor and costs an hour.
- Label rewritten claims too, since they are new claims.

**Metrics:**

| Metric | Definition |
|---|---|
| Unsupported-claim rate (before) | % of draft claims labeled unsupported |
| Unsupported-claim rate (after) | same, on claims that survive the verifier |
| Citation precision | supported / total claims in final report |
| Verifier catch rate | % of human-unsupported claims the verifier flagged |
| Verifier false-drop rate | % of human-supported claims it wrongly dropped |
| Retention | claims kept / claims drafted (guards against "drop everything" gaming) |
| Cost per report | median and p95 tokens, plus modeled USD |
| Verifier test-set P/R | precision/recall on `unsupported`, per perturbation type |
| Latency per report | median and p95 minutes |
| Budget adherence | % of jobs within `max_tokens` and `max_minutes` (target 100%) |
| Single vs multi | accuracy, cost, time, and coverage of sub-questions |

**Expectations, not claims:** unverified LLM drafts commonly show a noticeable unsupported rate (something like 10-25%), and a good verifier should push it low single digits at some retention cost. Report whatever you actually measure, including a weak result with analysis. An honest "verifier catches 80%, falsely drops 6%" beats a suspicious 99%.

**Suggested targets for the default budget:** under about 60K tokens and under about 8 minutes per report (rate-limit waits included). Adjust after measuring.

## 10. Tech stack

Python 3.12 (managed with `uv`), FastAPI + Pydantic, SQLAlchemy 2.0 async + Alembic, Postgres + pgvector, Redis + arq, `httpx`, `trafilatura`, Tavily or Brave for search, Groq free tier with two model families (writer and verifier), local embeddings via `sentence-transformers` (bge-small, 384 dims), `rapidfuzz`, LangGraph + `langgraph-checkpoint-postgres` for orchestration and crash-resume, official `mcp` Python SDK for the MCP tool, pytest, ruff, GitHub Actions, Docker Compose, then Railway/Render/Fly for the live demo. Stretch: Hugging Face `transformers` for the fine-tuned verifier. Optional: Langfuse or OpenTelemetry traces. LangGraph only: no LangChain models/chains/retrievers, LlamaIndex or CrewAI (see the framework rule in section 5).

**One correction to my earlier FastAPI code:** single mode must not be `sqs[:1]`. That would research only one sub-question and make the comparison unfair. Single mode should process *all* sub-questions sequentially in one loop. Multi mode runs them as isolated parallel workers.

## 12. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Verifier is itself wrong | Test set first (9.0); measure against human labels; report catch and false-drop rates |
| Groq free-tier quota (8K TPM / 200K TPD per model) | Token budgets, rate-aware scheduler, disk cache, shadow mode (B+C in one run), separate writer/verifier quotas, eval spread over days |
| Live demo hits rate limits | Gallery of cached reports is the primary demo; live endpoint is best-effort with a small default budget |
| Paywalled or JS-heavy pages | Skip and log; prefer sources that fetch cleanly; stretch: a rendering fallback |
| Labeling takes too long | 12-15 claims per report, CSV-based labeling, label the subset for single mode |
| Fine-tune eats the schedule | It is a stretch; timebox to 2 days, ship the negative result if needed |
| Scope creep | Follow the cut-list below |
